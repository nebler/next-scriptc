# CO1: Nitro route offload to Cloudflare Containers

2026-11-02. **Architecturally yes; production latency and Docker execution remain unvalidated.** A Worker can select a route and address a Container through a Durable Object. Its Node build can load a real N-API addon. In the available local experiment, forwarding heavy requests to **host macOS Node**, rather than a container, beats Worker JS by about 4.1–4.3×. This is evidence for further investigation, not a measured Cloudflare Containers win. Workers and Containers have the same marginal CPU-second rate. Native acceleration can lower compute cost, but provisioned memory/disk, DO usage and idle tails can erase the saving.

## What ran and what failed

The small [prototype](prototypes/container-offload/RUN.md) builds the same Nitro 2.13.5 app for `node-server` with `scriptc-promote/nitro`, and for `cloudflare_module` without the Node adapter. `/numeric?n=` creates an internal 1,024-element Int32Array and performs a deterministic multiply/add/checksum loop. The JSON boundary is one scalar argument and one scalar result. No large input encoder is involved. `/trivial` returns a constant object. `/binding` reads a local KV key in Workers and returns 503 in Node because `event.context.cloudflare.env.KV` is absent. `/state` is a local research diagnostic and is excluded from offload.

`offload.json` lists exact routes. Only GET requests qualify. The shared forwarder preserves status, headers and body, adds `x-co1-path: worker | node | worker-fallback`, and falls back on exceptions, 5xx responses or a one-second deadline. A deliberate refused localhost connection tests unavailability. Node's KV failure tests 5xx fallback. Non-selected paths and writes stay in Workers. Two focused tests cover these cases including timeout. There is no arbitrary origin URL or binding proxy exposed to clients.

The Container entry uses `Container`, `getContainer`, a DO binding, port 8080, a stable `co1` instance, and `sleepAfter='30s'`. Its final cold policy checks `getState()`, starts an unhealthy instance in `waitUntil`, and serves that request in Workers. This cold-state branch bundles successfully but **could not be executed**. The measured localhost version uses direct HTTP and has no DO state-check hop. It models a warm forwarding path only. The Dockerfile builds the Node addon inside Linux amd64, rather than copying a macOS addon. It includes Zig, Node headers and scriptc installation, but **the Dockerfile has not been built**.

Both Docker contexts fail with `Cannot connect to the Docker daemon at unix:///Users/noah/.docker/run/docker.sock. Is the docker daemon running?` The default socket links to that missing socket. `wrangler dev --local` with the Dockerfile fails with `The Docker CLI is needed to build the configured image before running dev but could not be launched.` [Exact logs](prototypes/container-offload/results/containers-attempt2.log) and [Docker diagnostic](prototypes/container-offload/results/docker.txt) are retained. Docker was not started or repaired, and no containers or images were created. Thus the requested plain-Docker fallback is blocked too. Container cold start is **unavailable, N=0**, not zero milliseconds. Host Node is an explicitly weaker third alternative.

Setup failures are retained: the discovery `sourceDir` initially pointed to a file, a first Nitro build omitted `srcDir: 'server'`, the legacy Worker preset needed a static-content manifest, and Wrangler rejected an unqualified local image name. The final app has all routes; local Wrangler uses `site.bucket` to provide that manifest. Initial build used Node 23 accidentally; all retained timing uses Node 24.22.0. No package or production adapter code changed.

## Method and results

Apple M4 Pro, arm64 macOS, 24 GiB RAM; Node 24.22.0, stock scriptc 0.4.6, wasm runtime 0.4.6, Wrangler 4.156.0, workerd 1.20261023.1, compatibility date 2026-10-30, `@cloudflare/containers` 0.3.7. Direct dependencies are pinned; transitive dependency resolutions are not locked. The app and addon are built entirely in this worktree.

The Node AUTO server trained for 1,000 requests at n=1,000 after one larger pilot call. Its scalar signature has one bucket regardless of n. The unchanged dispatcher promoted at call 609 after 26 verified shadows; the retained final snapshot has 690 foreground native calls, 28 verified shadows and zero fallbacks. Training at a small n is a prototype limitation. It does not establish a production size policy.

Each large case receives 15 warmups per lane, then six blocks of ten requests per lane, rotating lane order. N=60 measured requests per cell; no failures or parity differences. The five lanes return identical JSON bytes within each size. Wall time is external HTTP through full body consumption. CPU comes from macOS libproc user+system counters, with Mach timebase conversion, around each block. Both Wrangler workerd processes are summed, and the Node process is added for forwarding. Client and sampler CPU are excluded. CPU entries are medians of six **batch averages**, with p10–p90 spread using the measurement script's discrete percentile rule. They are not per-request CPU percentiles or Cloudflare billed CPU. No build, tests or other task computation ran concurrently with timing. Background host activity was not isolated.

The stock wasm reactor reuses the existing repository compute-only WASI bridge. It shadows the first three requests and every 32nd call, disabling on mismatch or trap. Those checks explain occasional long maxima: at n=300,000 the wasm maximum is 340.60 ms, versus p90 130.63 ms. Node AUTO also retains periodic JS checks, including a 62.67 ms maximum at n=100,000. Samples are not filtered. Final smoke adds an explicit wasm response header and `/wasm-state`; the original timed version used the same computation and verification, without that diagnostic header. Wasm is about 1.66× faster than JS on this internal typed-array loop. That does not contradict CF1's 6–11% loss on the large JSON revenue workload. Node native is about 4× faster than Node JS. Both results depend on compute intensity and boundary shape.

For trivial routes, N=240 per path after 30 warmups: in-Worker p50 **2.757 ms**, p10–p90 **2.511–3.467**; forwarded **1.646 ms**, **1.436–2.259**; unavailable-origin fallback **3.143 ms**, **2.889–4.065**. The forwarded-minus-Worker delta is **−1.111 ms**. This is a full framework-path comparison, not negative network latency: Nitro's workerd route machinery costs more here than host Node. A later direct Node control, N=60 after ten warmups, is **0.207 ms**, **0.164–0.253**. Its difference from forwarded trivial is an approximate **1.44 ms incremental HTTP hop**, across separate windows. Numeric forwarded-minus-direct-Node medians are **2.06 and 2.62 ms**. None of these include Cloudflare's DO RPC, placement, WAN distance or VM scheduling.

## Latency break-even depends on the real hop

Let C be Worker CPU milliseconds, S the speed ratio on equivalent hardware, and H the extra warm route latency. Then offload wins when `C > H / (1 - 1/S)`. The two measured sizes imply S≈4.5 comparing Worker compute slopes with Node native. With H≈1.44–2.62 ms, the equal-framework warm estimate is **C≈1.9–3.4 ms**. Use **about 4 ms** as a local planning threshold, not a verified production minimum. Against this workload's faster wasm baseline, S≈2.7 makes the upper estimate about 4.2 ms.

The actual full-route experiment has no positive observed crossover: even the trivial route forwards faster. An additional N=60 per path at n=1k, 5k and 10k gives Worker/forward p50 **2.865/1.314**, **4.447/1.678**, **7.012/2.204 ms**, respectively. Thus the formula deliberately separates compute savings from framework baseline effects; it extrapolates below the main measured CPU range.

For a real deployment use `H = DO checks + routing + network + queueing`, and include native calibration/shadow costs. A hypothetical 20 ms hop with 4× native speed requires C>26.7 ms; a 50 ms hop requires C>66.7 ms. These are scenarios, not Cloudflare measurements. If cold requests wait K milliseconds, replace H by H+K for those requests. The supplied Container entry instead serves cold requests locally while warming in the background. Restarting loses dispatcher learning. Container VM cold start, deployment CPU performance, CPU-share throttling, concurrency, geography, placement and warm-hit rate cannot be established without Docker and then a separately authorized deployment.

## Bindings require an explicit bridge

Node does not inherit a live `env.KV`, D1 database, R2 bucket or DO stub. In this prototype direct Node `/binding` is 503; forwarding it returns Worker fallback with `{"value":null}` from the local empty KV. This is availability preservation, not transparent Node binding support.

Cloudflare now documents [outbound handlers for Workers bindings](https://developers.cloudflare.com/containers/configuration/workers-connections/). A container can fetch a virtual HTTP hostname such as `http://my.kv/key`; a Worker handler uses its own configured bindings. [Outbound interception](https://developers.cloudflare.com/containers/configuration/outbound-traffic/) requires exporting `ContainerProxy`, supports local development, and can apply host allowlists and disable general internet access. This is a supported bridge, not direct Node access to Worker runtime objects. The prototype deliberately does not implement it.

A binding adapter would implement a narrow versioned protocol, not serialize a binding object. KV needs get/put/list/delete options and metadata; R2 needs streaming, conditional and range operations; D1 needs prepared statements, batch results and session/bookmark semantics; DO needs namespace/object identity and method dispatch. Enforce operation and key permissions, request limits, per-instance authorization, deadlines and errors. Batch calls to avoid one round trip per item. Preserve streaming backpressure and avoid replaying writes after ambiguous failure. Existing Node app binding access needs an injected facade or explicit dependency interface. A generic object RPC wrapper cannot promise identical transactions, consistency or capabilities. Each bridge adds Worker execution and the backing service's charges; its overhead is unmeasured here.

## Pricing and lifecycle

[Workers Standard pricing](https://developers.cloudflare.com/workers/platform/pricing/) includes 10 million requests and 30 million CPU ms per month in the $5 plan. Overage is $0.30/million requests and $0.02/million CPU ms. Waiting for I/O does not add Worker CPU, and Worker subrequests are not additional inbound requests.

[Containers pricing](https://developers.cloudflare.com/containers/platform/pricing/) meters active CPU at $0.000020/vCPU-second, provisioned memory at $0.0000025/GiB-second and disk at $0.00000007/GB-second, in 10 ms increments while running. Included monthly amounts are 375 vCPU-minutes, 25 GiB-hours and 200 GB-hours. Memory and disk continue while idle until sleep. Network egress is region dependent, starting at $0.025/GB in North America and Europe after the included allotment. Worker and DO usage is billed too. The `standard-2` configuration provisions 1 vCPU, 6 GiB RAM and 12 GB disk. Its idle memory+disk rate is **$0.00001584/second**, or **$0.0004752 per 30-second idle tail** before allowances. Counts and rates are as retrieved on 2026-11-02, not a quotation for a specific account.

[DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) includes one million requests and 400,000 GB-s monthly on Paid, then $0.15/million requests and $12.50/million GB-s. Duration follows active wall time and the 128 MB isolate allocation, with concurrency sharing duration. The final cold-policy status RPC can add a DO request beyond `fetch`; lifecycle calls and alarms add usage too.

A rough marginal example **above every allowance**, excluding logs, egress, bindings, cold starts and rounding, illustrates why latency and price differ. Suppose Worker JS uses 100 CPU ms and native needs 25 CPU ms on a full core. Worker CPU costs **$0.000002/request**. Native CPU alone costs **$0.0000005/request**, a 75% saving at 4× acceleration. At full utilization the container's 25 ms memory/disk share adds $0.000000396. A 25 ms active DO window adds roughly $0.00000004 at 128 MB, and each DO request adds $0.00000015. With two DO requests and the common $0.0000003 inbound Worker request, offload totals roughly **$0.00000154/request**, versus **$0.0000023** in Workers, about 33% less before forwarding CPU. Real allocation can differ, and DO duration is shared across concurrent requests. A single isolated request followed by a 30-second sleep tail adds about **$0.000475**, far larger than compute. With a 2 ms routing CPU allowance, the warm offload example is about $0.00000158, saving $0.00000072/request. Amortizing a whole 30-second tail then needs about 660 such requests per burst, ignoring cold startup. At sustained arrival rate R, memory/disk alone allocates $0.00001584/R per request, so this example needs roughly 14.2 requests/second on the instance before that fixed running cost fits under its remaining CPU saving. Its ideal serial capacity at 25 ms native CPU is 40 requests/second; queueing can reduce the latency advantage near capacity. These estimates use a full-core standard-2 instance and must be recomputed for other types. Monthly included pools can make either marginal bill zero at low volume. This is not a billing forecast based on local CPU counters.

[Container class lifecycle](https://developers.cloudflare.com/containers/api/container-class/) defaults to ten minutes before sleep; this prototype uses 30 seconds. `fetch()` normally starts a stopped container and waits for its port. The cold-policy status check changes that behavior. [Scaling and routing](https://developers.cloudflare.com/containers/configuration/scaling-and-routing/) use explicit stable IDs or random selection among a fixed number of instances. `max_instances` caps simultaneously running instances; it is not an autoscaling policy or a queue. One stable name concentrates synchronous Node CPU work on one process. Use a bounded pool and backpressure for parallelism. [Local development](https://developers.cloudflare.com/containers/guides/local-dev/) requires Docker, does not enforce `max_instances`, and leaves images after sessions. [Lifecycle architecture](https://developers.cloudflare.com/containers/concepts/architecture/) explains cold placement; local HTTP cannot reproduce it.

## Verdict and adapter requirements

Pursue this for opt-in, replay-safe, compute-heavy routes where native acceleration clears the real network hop. A busy instance may reduce total cost; sparse traffic can become much more expensive. Keep binding-heavy routes in Workers until a narrow bridge is justified. The local experiment supports the compute premise and fallback design, but **does not validate Cloudflare Containers execution, cold latency or production break-even**.

An opt-in Nitro adapter would need two builds from the same source revision, Linux amd64 native artifacts, an exact method/path policy, Worker fallback availability, request replay rules, response/stream handling, bounded deadlines and cancellation, cold-state handling, health/circuit breaking, a bounded instance pool, queue limits, binding dependency declarations, and observable serving-path headers/counters. It must include dispatcher learning after restarts and use measured production route/input buckets. This research adds no such package API.

The timeout prototype does not cancel an underlying DO start or synchronous native computation; abandoned work can still run. It retries only read routes. Production needs explicit authorization for any side-effectful handler, and an idempotency protocol where fallback can duplicate execution. Container SDK, Docker build, cold branch and binding interception still need executable validation before an adapter proposal is considered complete.

All changes stay in this worktree. No login, deployment, Cloudflare account call, push or PR occurred. No existing Docker resource was touched. Generated dependencies, addons, wasm, output directories and tarballs are removed after verification; only small source and evidence files are committed.
