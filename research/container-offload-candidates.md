# Container offload candidate census

2026-11-02. Heavy, binding-separable routes exist, most clearly in image codecs and password hashing. This search did **not** establish a heavy JavaScript function that scriptc can profitably promote in a real Workers app. Keep container offload opt-in and validate one actual route before building an automatic product around it.

## Scope and evidence

I shallow-cloned and inspected 12 Workers-targeting repositories under `/tmp/nsc-co2-census`, then deleted the clones. The table includes 11 projects with an OSS license declaration and one source-available search system, explicitly excluded from the OSS denominator. Two projects declare MIT only in package metadata or documentation, without a license file. Deployment support means a checked-in Worker handler plus config or deployment instructions. It does not prove a currently live deployment. This sample includes small services and framework examples, not 11 independent production applications.

Selection deliberately favored image, OG, crypto, search, analytics and map workloads. It is not a prevalence sample of the Workers ecosystem. Source inspection can identify likely expensive input sizes, but it cannot prove tens or hundreds of milliseconds of request CPU. No candidate app was installed, executed, deployed, or benchmarked here. All CPU labels below are source-based assessments or attributed upstream claims, not our measurements. Cache-hit routes generally have no offload value.

The three tests are heavy CPU, numeric or typed compute dominance, and bindings separable from the compute. A strong source-level candidate satisfies the last two and plausibly the first on expensive inputs. A conditional candidate still needs profiling to separate layout, parsing, asset I/O and rasterization. Automatic promotion has a fourth requirement: an extractable sync pure function in a supported language and boundary.

## What qualifies, and how common is it?

Among the 11 license-declared OSS projects, five are strong source-level candidates: four image pipelines, including one already using Containers, and Argon2. Four OG generators are conditional because layout and string processing share the route with rasterization. Two are rejected: Counterscale delegates aggregation to Analytics Engine, and protomap-worker reads existing tiles. The separately listed source-available search project is also rejected for numeric promotion. These counts describe a targeted discovery sample, not a percentage of Workers apps. Measured qualifying routes: zero, since route CPU was not measured.

The positive cases overwhelmingly call compiled libraries. Replacing a Wasm codec with native Rust or a Node addon is different from scriptc compiling the app's JS. Likewise, moving an entire Next/React Router route does not make its database and object-processing work a good compiler target. No convincing in-app numerical scoring, geospatial generation, or dense JS analytics route emerged in this bounded search.

Existing Container use in cloudflare-worker-image is especially informative. Its Worker keeps caching and selection at the edge, then forwards an image request to a Rust server. It does not require a transparent replica of every Worker binding inside Node. The image and crypto workloads justify this explicit split even if scriptc contributes no speedup.

## Existing census tooling and measured source discovery

`research/coverage-baseline/census.mjs` is pinned to Papermark, Dub and Umami and requires their dependencies. Framework scripts under `scripts/` are also pin-gated. I used their shared `discoverPromotions` API through [container-offload-census.mjs](prototypes/container-offload-census.mjs), without changing production code. [Raw discovery output](container-offload-census.json) contains all accepted functions and diagnostics.

| Source tree | Source files visited | Accepted functions | Reported rejection diagnostics |
|---|---:|---|---:|
| og-link `src` | 2 | 0 | 1 |
| cloudflare-worker-image-cdn `src` | 8 | 1: `snapToStep` | 10 |
| protomap-worker `src` | 61 | 3: `timingSafeEqual`, `_resolveAllowedOrigin`, `hexToBytes` | 9 |

The diagnostics count is not a rejected-functions denominator. Async handlers, nested callbacks and other early exclusions can be silent. The existing scanner skips test directories but visits colocated `.test.ts` files; five protomap diagnostics are test helpers. Discovery acceptance is not native compilation, successful shadow verification, or a performance win. `snapToStep` scans a short configuration list. The other accepted helpers compare short authentication byte strings, match CORS origins, or decode hex. None establishes a heavy request kernel. In particular, preserve constant-time security behavior before considering any compilation of `timingSafeEqual`.

Top blockers are opaque Wasm imports, async entry points, runtime Response/Headers objects, ArrayBuffer method types at the JSON boundary, state/effect proofs, and functions too small to pass the work screen. og-link's synchronous decoder fails on unsupported `atob`. The CDN's `downscale` reports an unresolved `@cf-wasm/photon` runtime import. App dependencies were intentionally not installed: that unresolved-import diagnostic is partly an environment limitation, not proof that a fully installed dependency graph would fail identically. The heavy operation still resides in a compiled Wasm package. TypeScript 5.9.3 and Babel 7.29.x came from a task-owned temporary dependency directory; the source-only scan is a lower-cost integration check, not a production app build.

Reproduce with shallow clones of the metadata URLs, check out the recorded SHAs, install app dependencies if a complete build census is needed, then run `node research/prototypes/container-offload-census.mjs /tmp/clone src`. The package's Babel dependencies and TypeScript resolution must be available. This run used temporary node_modules symlinks into `/tmp/nsc-co2-tools`; all task symlinks were removed afterward. No app lifecycle scripts ran.

## Recommendation

Finish the sibling's local route-forwarding proof, but require an actual compute-heavy application route as the next gate. Compare Worker JS/Wasm, warm-container Node JS, and warm-container native on identical inputs. Measure cold-start latency and Worker transport CPU separately. Use a binary body for images rather than JSON arrays of pixels. Keep auth, cache and storage at the Worker edges when possible.

Only a route whose compute saving exceeds forwarding, encoding, binding callbacks and cold-start amortization should move. Current evidence supports a small explicit container escape hatch for codec/crypto services. It does not support general automatic scriptc offload for Workers frameworks. The [binding proxy experiment](binding-proxy.md) makes edge I/O practical, but does not change that demand-side conclusion.

## Exclusions and access failures

Ackee and pii-sanitizer-gateway were also shallow-cloned during discovery, then excluded before the table. Ackee did not establish Workers deployment support in this inspection. The PII gateway's apparent cost was regex/string handling and upstream LLM calls, and no license declaration was found in its root package metadata or license file. No clone or discovery invocation in the reported sample failed. No third-party code was committed; all 14 discovery clones were deleted.
