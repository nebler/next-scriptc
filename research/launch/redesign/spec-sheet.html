Method, scope and sources

What the headline covers. “TypeScript faster than Go + SIMD” is the server-compute result only, which is why the label Vector-search server compute sits directly under it and the caveat gives the full-request medians. It is not an end-to-end or general speed claim.

120 requests. 3 fresh preview deployments × 40 measured requests, each after 10 warmups, sent one at a time on a keep-alive connection. Every response returned the identical top-10.

Server compute vs loop only. Server compute (this chart) times the whole handler inside the hosted function: parse the request, scan all 100,000 rows, pick the top 10, build the JSON response. The loop-only chart times just the scan in a Sandbox, with no HTTP, JSON or platform at all. It is supplemental evidence that the lead comes from the search loop itself.

Process CPU for the same requests (mean ms/request): Native TypeScript 9.969, Go + SIMD (experimental) 14.405, Go 43.287, Node.js 76.472. Go excludes its separate IPC proxy.

Replaces “Int8 search on Vercel Functions”. Headline describes the work (find the 10 closest of 100,000 embeddings); int8 and 768 dimensions live in these notes. Server-side compute p50 on Vercel Functions iad1, request parse → top-10 → JSON, 3 fresh preview sets × 40 C=1 requests per variant, identical top-10 on every response. The timer runs inside the function (request parse → top-10 → JSON); network, platform routing and IPC are outside it. Full requests are about even: client-observed median 156.972 vs 160.152 ms (native vs Go SIMD), p95 249.987 vs 247.778 ms, and at 4 concurrent requests native loses (see the Spec Sheet page). Native = patched scriptc with CPU dispatch; stock scriptc with Math.imul already reaches 10.087 ms. Go SIMD = experimental simd/archsimd. Source: research/vector-vercel.md#measurements.

Vector search: memory (4 runtimes)

Method, scope and sources

Spec Sheet only (new). Same hosted run, same 120 C=1 requests as the server-compute chart: median post-work serving-process RSS, native 81.137, Go SIMD 81.789, Go 81.82, Node 153.711 MiB. Every runtime holds the same 100,000×768 int8 corpus (76,800,000 bytes ≈ 73 MiB), so most of each bar is the data and native and Go are effectively tied (native is 0.7 MiB lower than Go SIMD, within instance/GC variation). Node is 1.89× native. Coverage: Go’s numbers exclude its separate IPC proxy process; native includes its in-process IPC runtime; Node includes all process threads. Process RSS only, not whole-instance, PSS or billed memory. Never compared with the hello-route 5.6/80 MiB values, which are a different workload and protocol. Source: research/vector-vercel.md#measurements.

Code: hello route

Method, scope and sources

Monolith, Editorial and Signal keep the original route.native.ts hello handler. Spec sheet (revised) adds the requested "use native" directive in the one place the adapter supports it in a route: a named module-level async function with a JSON result (greet), called from an ordinary route.ts GET. Inside route.native.ts the directive would be a silent no-op (those files are skipped by function extraction, packages/next-scriptc/src/functions/extract.mjs), and a file-level directive in any route file fails the build (src/routes.mjs). The generator runs the real extractor on the snippet and asserts it finds greet. Caveat: function-level "use native" currently runs on Node on Vercel (README); only route.native.ts deploys as a native Vercel Function. The Spec Sheet hero therefore keeps the route.native.ts snippet.

Where Go numbers exist (and where they don’t)

  • Vector search, hosted: matched four-runtime data for server compute, process CPU, process memory and full-request time, all from one run (vector-vercel.md). Shown: compute and memory charts, the full-request table above.
  • Hello, revenue, nearby-store CPU; hello-route memory; first response after deploy: measured native vs Node.js only (vercel-final.md). No matched Go measurement exists for these routes, so those charts stay two-way. Adding Go would need a new benchmark.
  • CSV / JSON / thumbnail / bcrypt routes (go-territory.md) have Go numbers, but the hosted Go run used a separate 1-vCPU load generator from the Node/native run, and these are different workloads. Not charted; mixing them into the charts above would be misleading. That report also records native losses (bcrypt, hosted JSON).
